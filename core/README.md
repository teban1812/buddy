# buddy-core (prototype)

The Buddy plugin for Claude Code and its Node core (ADR-002: Node, git, markdown with front matter, no packaged executable, no dependencies). Built from the M0 prototypes and the design in `docs/design/`.

**Install** (in the folder of the project): `claude plugin marketplace add teban1812/buddy --scope local`, then `claude plugin install buddy@buddy --scope local` (add `#<tag>`, such as `teban1812/buddy#v0.4.0`, to pin a version).

```bash
cd core && npm test                       # about 500 tests, no network, no model calls
node core/bin/buddy.mjs help             # one entry point (also `bin: buddy` in package.json)
node core/bin/scope.mjs --repo <dir> --base <ref> [--head <ref>] --request-file req.txt --answers answers.json [--batch question-batch.md] [--context docs/context.md] [--judge | --judge-request] [--json]
```

## init, library, context add, feedback (a project created with Buddy)

To design a library of your own, read [`LIBRARY-GUIDE.md`](LIBRARY-GUIDE.md): each part of a library and what Buddy does with it, with an example of each.

```bash
node core/bin/buddy.mjs init [--library <git url or folder>] [--version <tag or commit>] [--profile <name>] [--host github|azure|none] [--answers <file>] [--no-template] [--repo <dir>]
node core/bin/buddy.mjs init --list-profiles [--library <git url or folder>] [--version <tag or commit>]   # the library's profiles and general questions; creates nothing
node core/bin/buddy.mjs init --questions --profile <name> [--library <git url or folder>] [--version <tag or commit>]   # that profile's questions, steps, normative documents and saved prompts; creates nothing
node core/bin/buddy.mjs init --permissions [--repo <dir>]                 # only the routine permissions, into .claude/settings.json
node core/bin/buddy.mjs library --set <git url or folder> [--version <tag>]  # once per user; kept in ~/.buddy/config.json
node core/bin/buddy.mjs library --show                                     # which library init would use, and why
node core/bin/buddy.mjs library --unset
node core/bin/buddy.mjs init --standards <folder> [--repo <dir>]          # a plain folder of standards instead of a library
node core/bin/buddy.mjs init --no-library [--repo <dir>]                  # no standards, no base application
node core/bin/buddy.mjs context add --section "<section>" --text "<the owner's words>" [--assumed] [--file docs/context.md]
node core/bin/buddy.mjs feedback "<what got in the way>"                     # one line to <factory>/docs/field-log.md
node core/bin/buddy.mjs feedback --factory <path of Buddy's repository>     # once per user; kept in ~/.buddy/config.json (BUDDY_FACTORY wins)
```
The formats of every part of a library (`library.json`, the standards and their open values, the templates, the questions, the steps and each template's prefill, the normative documents, the saved prompts) and what Buddy refuses in each are in [`LIBRARY-GUIDE.md`](LIBRARY-GUIDE.md); what follows is what `init` does with them.

**Choosing the library.** First match wins (R104): the command's own `--library`; the `BUDDY_LIBRARY` variable (`<git url or folder>`, or `<git url or folder>#<version>`: the text after the last `#` is the version, so a library address cannot contain `#`); the library kept by `buddy library --set` in the user's `~/.buddy/config.json` (the same file as the factory path; a folder is kept as its absolute path and must exist, a URL is kept as written and never reached by `--set`); else Buddy's public default library (`DEFAULT_LIBRARY` in `src/init.mjs`: its URL only, no fixed version), reached with the user's own git credentials (no password prompt: `GIT_TERMINAL_PROMPT=0`). `library --show` prints the library, its version and why that source won (and which configured library the variable is hiding), offline; `--unset` removes it from the configuration. Addresses are always shown without the user name, password, token or query of a URL. Every report ends with a `Library:` line: which library and version, why that one, and how to use another.

**Reading it.** The version is `--version`, else the one the chosen source carries (`#<version>` or `--set … --version`), else, for a library reached by URL, its latest published version: `git ls-remote --tags`, the highest semantic-version tag (`v1.2.3` or `1.2.3`; pre-release tags only when there is nothing else); a library with no version tags is read at its default branch and the report and the note say so. A local folder without a version is read at its last commit. The library is fetched shallow at its version into a temporary folder, so the project receives only what it has committed (uncommitted changes are left out and the report says so); a local folder not in git is copied as it is, without `node_modules`, `bin`, `obj`, `dist` and `.git`, and reported as not versioned. A library declares in `library.json` the contract it follows (none means 1); Buddy understands those in `CONTRACTS` (`src/init.mjs`) and refuses a higher one saying a newer Buddy is needed. Every part is checked before anything is written; a malformed one stops `init`, naming the file and why. A project that already has `docs/standards/` reads no library, so a second run needs no network.

**Questions and answers.** `init --list-profiles` prints each profile with its line from `library.json` (`general` left out; a library without `library.json` lists the folders of its `standards/` and `templates/` without descriptions), the profile used without `--profile` (the library's `default_profile`, else `dotnet-react`), the contract, the library's general questions, and the library, version and commit; it writes nothing. `init --questions --profile <profile>` prints that profile's questions, its steps (with how many items its template decides), the normative documents and the saved prompts; it writes nothing either. Buddy asks the questions, recommends a profile and the owner chooses (`agents/buddy.md`). `--answers <file>` (`{ "<question id>": "<answer>" }`) puts each answer in `docs/context.md`, in its question's section with the question and why it is asked, and fills the open value `{{name}}` its question names in the project's standards; an open value left unanswered is reported as still to be defined, and an answer to a question the library does not ask is refused.

**The birth.** `init` runs `git init` when the folder is not inside a git repository (inside one, it uses it), and creates:
- `docs/buddy/backlog/` (where changes of no milestone are recorded; a project that still has `docs/buddy/changes/` keeps it, and `buddy migrate` moves it);
- `docs/inputs/` with a short README (what the owner hands over: the PRD, the prototype, specifications; Buddy reads them and never changes them, R106; an existing one is left as it is);
- `docs/context.md` with the sections Purpose and outcomes, Users, Constraints, Risk appetite and Unknowns, empty except the answers and one `unknown` line saying the business is still to be told (so the file passes `context check` and `verify` from the start; the risk appetite is `missing` until the owner describes it). The program writes it in English and has no table of languages: when the owner chose another documentation language, Buddy rewrites it whole in that language right after init (`skills/new-project/SKILL.md`) and names its risk section in the header (`risk_section`);
- **Standards.** `standards/general/` goes to `docs/standards/general/` and `standards/<profile>/` to `docs/standards/<profile>/`, with the open values filled, and one `docs/standards/ORIGIN.md` covering both (library address without credentials, where it came from, profile, which folders were copied, version requested (`latest: v1.2.0` when none was asked), commit, and how to move to a newer version by copying it over). A profile without standards of its own gets only the general ones, a library without `standards/general/` gives only the profile's, and both cases are said; a profile with neither standards nor a template is refused, and `general` is not a profile (R103). With `--standards <folder>` that folder is copied instead (without its `.git`), and `ORIGIN.md` gives its absolute path and, when it is in git, its commit and whether it had uncommitted changes.
- **Template and renaming.** Before writing anything, init looks at the folder: any entry at its top other than `.git`, `docs`, `README*`, `LICENSE*`, `.gitignore`, `.gitattributes`, `.editorconfig`, `.claude` and the operating system's `.DS_Store`, `Thumbs.db` and `desktop.ini` (compared without case) makes it an existing project (see below). Otherwise, unless `--no-template`, `templates/<profile>/` is copied to the project's root without the library's history, with `BuddyApp` and `buddy-app` replaced in names and text contents by the folder's name in PascalCase and kebab-case (ASCII-folded; a name that cannot start a C# identifier is refused before anything is written); a file that already exists is left as it was and listed.
- **Pipeline by host (R112).** A template may bring `.github/workflows/` (GitHub Actions) and `azure-pipelines.yml` (Azure Pipelines). Then `--host github|azure|none` is required (without it init refuses before writing anything and names the three choices): the project keeps only that host's pipeline, or none. The report says which pipeline the project was born with and `ORIGIN.md` records it in a `Repository host` line. A template without pipeline files, an existing project, `--no-template` and `--list-profiles` need no `--host`.
- **Steps and their records.** Each step of the profile is copied to `docs/steps/<step>/` and its record written at the step's `record` path: an item the template's prefill decides, in a file the project was born with, is written `decided` with that file; every other item is `unknown`, for Buddy to draft once the first milestone's plan says what will be built, and the owner to confirm line by line (`buddy context confirm <record> --line <n> --by owner`), then approve whole (`buddy context approve <record> --by owner`, which writes who, when and a fingerprint of the record). Until every line is decided or confirmed and the record is approved as it is now, no change can move to `building` (an edit after the approval makes it stale), and the board lists the record as waiting for the owner.
- **Normative index.** The library's `normative/index.md` is copied to `docs/standards/normative.md`; never a document.
- **Saved prompts.** Each saved prompt of the profile is copied, folder and all, to `.claude/skills/<name>/`; one already there is kept.
- **First decision record.** `docs/decisions/` gets the project's first decision record (MADR 4, as `buddy decide` writes it): the library, its version, the profile and the base application it is born from, with every profile as the options considered. A template's own records in `docs/decisions/` come with it.
- **Permissions.** The routine permissions go into `.claude/settings.json` (Buddy's program, the project's checks, local git; never a push, a deletion or an installation), merged with what is there; `init --permissions` writes only those, for a project that already exists or after a plugin update.
- **First commit and health check.** Everything init made is committed as the project's first commit (`chore: born from <library> <version>, profile <profile>`), naming each file; when git does not know the user, or refuses, it is left uncommitted and the report says why. Then, only when a template was copied, `npm run setup` (if the project has it) and the validate command run once, with time limits (15 and 10 minutes; the whole process tree is stopped on timeout), and the report says in plain words whether the project is born healthy; a failure does not fail `init`.

It never overwrites: an existing `docs/context.md`, `docs/standards/`, step record or saved prompt is reported and left alone, and a second run changes nothing.

**Existing projects.** A folder that already holds a project gets the standards, the steps (every item to draft), the normative index and the saved prompts, but no template; the report lists what it found and says that the standards apply to the code each change writes from now on and that existing code that is not touched is not forced to follow them.

**context add.** Appends one statement at the end of a section of the file (any `##` heading it has; an unknown one is refused with the list), tagged `human <today>` or, with `--assumed`, `assumed`, and moves `updated:`; the same words already in that section are not written twice.

**feedback (R100).** Appends `| date | project | Buddy version | text |` to the factory's `docs/field-log.md` (created with its header when missing); the project is the folder name of the current git root and the version comes from `core/.claude-plugin/plugin.json`; nothing is written into the current project, and without a factory it refuses and says how to set one.

`buddy init` also writes a **`CLAUDE.md`** with a short block between two markers (`<!-- buddy:begin … -->` … `<!-- buddy:end -->`): that the project is built with Buddy, where to read first (`docs/context.md`, `docs/standards/`, `docs/inputs/`, `docs/buddy/`) and the commit rules. It holds only stable pointers, because what is written at birth is not corrected by a plugin update; the long instructions stay in the plugin. If the library's template brings its own `CLAUDE.md`, Buddy's block goes first and the template's text is kept; a `CLAUDE.md` the folder already had is only appended to; running `init` again keeps the block (or brings it up to date) and never touches what is outside the markers. The checkpoint treats `CLAUDE.md` as a protected file.

## scope (task 1)
Traces every addition in a diff to a human answer, a stated risk (the context's risk-appetite lines), the request alone, or the agent's own initiative, and reports shares of added lines. A term-overlap pre-pass places hunks (windows of 8 added lines); answers and risks are credited only for terms beyond the request's own vocabulary. `--judge` asks Haiku (`claude -p`) to place the hunks the pre-pass cannot; `--judge-request` also re-checks hunks attributed to the request alone, because the request's vocabulary is shared by every hunk and can hide rules the request never stated. The shares are indicative, not exact; the judge's accuracy has not been measured.

## queue (task 2)
```bash
node core/bin/queue.mjs new --in spec.json [--slice <name>] [--out <file>]   # batch from a JSON spec (situation, options with cost, recommended, default, blocking); for a change or slice, questions-<n>.md in its change folder; for a milestone, in the milestone's folder; otherwise docs/questions.md
node core/bin/queue.mjs show|status docs/questions.md                # cards; status exits 3 while a blocking question is open
node core/bin/queue.mjs answer docs/questions.md --q <id> --option a # or --text "..." or --delegated ("your call")
node core/bin/queue.mjs assume docs/questions.md                     # proceed on the defaults of open non-blocking questions (origin: assumed)
node core/bin/queue.mjs analyse docs/questions.md --request "..." --context docs/context.md   # answer analysis (claude -p); writes <file>.roundN.md
node core/bin/queue.mjs defaults docs/questions.md                   # assumed defaults nobody has confirmed (exit 1 if any)
```
Port of `probes/queue/followup_analysis.py` with structured follow-ups (options with cost, recommendation, default), a cap of 3 follow-ups per round and 2 follow-up rounds in total; beyond the limit they are recorded as assumed defaults. The default path `docs/questions.md` follows the cloud plan; design question Q4 proposes one file per batch. `core/test/fixture-c3-spec.json` is the saved Part C3 question set. **Questions at the level of a milestone (R108)**: `--slice <milestone name>` (or the spec's `slice`) links the batch to the milestone and writes it in the milestone's folder (`docs/buddy/milestones/<date>-<name>/questions-<n>.md`): the intake's one round of costly questions for the milestone, before its changes exist. As for a change, the milestone cannot be made `ready` while a blocking question of its batches is open, the board lists it as `answer: <situation> (for <milestone title>)`, and renaming the milestone while refining moves its batches and rewrites their `slice`.

## context (task 3)
```bash
node core/bin/context.mjs intake --notes notes.txt --out docs/context.md [--facts PROJECT-FACTS.md]   # draft or merge; everything drafted is assumed or unknown
node core/bin/context.mjs card docs/context.md                    # the confirmation card for the owner
node core/bin/context.mjs confirm docs/context.md --all-risk      # or --line N [--text "corrected text"]; only the owner runs this
node core/bin/context.mjs accept-assumed docs/context.md          # go on with the risk appetite left assumed, on purpose
node core/bin/context.mjs check docs/context.md --require-risk-confirmed   # the gate: exit 1 while the risk appetite is neither confirmed nor accepted as assumed
```
The risk appetite is read from the section the context's header names (`risk_section: <heading>`, for a context written in another language), or from the heading `Risk appetite` when it names none. `check`, `card`, `confirm --all-risk`, `verify`, the board, the checkpoint and `scope --context` all read it there. A context whose named section does not exist or has no line is refused by `check` and `verify` (exit 1), which say the section they looked for. The origin tags (`human`, `assumed`, `unknown`) are English in every context.
States: `confirmed`, `accepted-assumed` (front matter `risk_assumed_accepted: <date>`), `blocked`, `missing`. The intake never writes `human`; with an existing file it keeps confirmed lines byte for byte and only appends new assumed items. Only `human` statements may answer a question (`suppressionSources`), and one older than 90 days stops counting until reconfirmed (design Q18).

## view (task 4)
```bash
node core/bin/view.mjs --dir <records folder> --out view.html [--scope scope.json] [--evidence evidence.json] [--repo . --base <ref>]
node core/bin/view.mjs --dir <records folder> --text      # the business-terms summary for the chat
```
One static page (no external assets, dark mode): outcome (built, left out, size), where the lines come from (the scope trace, or "not measured"), what needs the owner (open findings, unanswered questions, assumed defaults computed from the batches), questions and answers with origin badges, decisions (superseded struck through), findings, evidence, commit trail. Sample: `docs/samples/c4-archive/` (transcribed by hand from the Part C4 notes; ids invented).

## slice (increment 3, schema `buddy/slice@1`)
```bash
node core/bin/buddy.mjs start "<title>" --request "<the Product Owner's words>" [--name <name>] [--kind feat|fix|...] [--ac "<criterion>"]... [--exclude "<what it does not include>"]... [--dep <id>]... [--branch <b>]   # opens a change
node core/bin/buddy.mjs start "<title>" --in <change> --request "<...>" [--name <name>] [...]   # adds a slice to a change (a change in several pieces)
node core/bin/buddy.mjs start "<title>" --milestone <milestone> --request "<...>" [...]        # opens a change in a milestone instead of the backlog
node core/bin/buddy.mjs milestone start "<title>" --name <name> --request "<the goal>" [--ac "<criterion>"]... [--exclude "<text>"]... [--branch <b>]   # opens a milestone
node core/bin/buddy.mjs move-to <change> <milestone name | backlog>   # moves a change's folder, everything in it, keeping its date and name
node core/bin/buddy.mjs status [--json]                       # in rank order, with steps done / total: each milestone with its changes, then the backlog
node core/bin/buddy.mjs slice rename <id> <new name> [--force] # while refining (frozen at ready, R87); --force for a migration: the commits already made keep the old name
node core/bin/buddy.mjs move <id> <state> [--by owner]        # only legal moves; accepted needs --by owner
node core/bin/buddy.mjs criteria add <id> "<text>" | criteria edit <id> <AC id> "<text>" | criteria remove <id> <AC id>   # while refining
node core/bin/buddy.mjs excludes add <id> "<text>" | excludes edit <id> <X id> "<text>" | excludes remove <id> <X id>      # while refining
node core/bin/buddy.mjs step add <id> "<text>" [--under <n>]  # numbered 1, 2, 2.1 ...
node core/bin/buddy.mjs step done|undo <id> <n>
node core/bin/buddy.mjs slice accept-card <id>                 # what to present to the Product Owner before accepting: the assumptions to confirm (R59)
node core/bin/buddy.mjs queue confirm <file> (--all | --q <id>) # the Product Owner approves what was assumed; accepting is refused until every assumption is confirmed
node core/bin/buddy.mjs verify <dir> --canonical              # a hand-edited slice that differs from what the program writes is a problem
```
(`start`, `step`, `status`, `move`, `criteria`, `excludes`, `milestone` and `move-to` are short forms of `buddy slice start|step|list|move|criteria|excludes|milestone|move-to`.) **Criteria and exclusions (R94, R109)**: a record carries `criteria` (AC1, AC2…: how it is accepted) and `excludes` (X1, X2…: what it does not include, in the owner's terms; "Nothing beyond the criteria above" is a valid one), given with `--ac` and `--exclude` at `start` and added, corrected or removed with `criteria|excludes add|edit|remove` while the record is `refining`; removing one does not renumber the others, a new one takes the highest id present plus one, and a criterion a step cites is not removed. From `ready` on they are refused: the goal is fixed when a change is ready, and changing it is the owner's decision, made by moving the change back to `refining` (R67). The accept card shows both, the exclusions after "You asked for". **Milestones and the backlog (R118)**: a milestone is `docs/buddy/milestones/<YYYY-MM-DD>-<name>/milestone.md`, a record of the same schema with `kind: milestone` (its goal is `request`, with its criteria and exclusions), and its changes live in `changes/` of that folder, each as below; the changes that belong to no milestone live in `docs/buddy/backlog/`. `start` opens a change in the backlog, or with `--milestone <name>` in that milestone; `move-to <change> <milestone | backlog>` moves the change's folder with everything in it (its slices, batches, decisions and evidence), keeping its date and name, so every reference by name still works; a slice moves with its change, and a milestone that is accepted or abandoned takes no change, by opening or by moving. A milestone moves through the same states with `move` and follows the ready rule; it has no steps (its work is its changes), and it is accepted only when every change of it is accepted or abandoned (its accept card lists them). Names are unique across milestones, changes and slices. `verify` checks that a milestone is the `milestone.md` of a folder named by its date and name under `docs/buddy/milestones/`, that a change is in `docs/buddy/backlog/` or in a milestone's `changes/` (whose `milestone.md` must exist), and that an accepted milestone has no open change. `docs/buddy/changes/`, the backlog of before R118, is read as the backlog until `buddy migrate` moves it. **One folder per change (R87)**: a change (a feature or a fix) is `<YYYY-MM-DD>-<name>/change.md` in one of those places, dated by the day it was opened; when it has more than one piece, each slice is `<slice name>.md` in the same folder (the folder replaces `epic:`), the change keeps no steps of its own and is accepted when every slice is accepted or abandoned. The folder also holds the change's question batches (`queue new --slice <id>` writes `questions-<n>.md` there) and its checkpoint evidence (`evidence/`, versioned with the change). A record without steps says so (`Steps: planned when the change is ready.`); the first step replaces that line. A slice id is a change name or a slice name, and names are unique across the repository. The flat layout of before R87 (`docs/buddy/slices/<id>.md`, `epic:`) is still read and written in place until `buddy migrate` moves it. The id is a name (R86): lowercase letters, digits and single hyphens, at most 40 characters (R89), proposed from the title (`Archive a book` gives `archive-a-book`, then `-2` if taken; a long title is cut at a word boundary, never on an empty word such as `and` or `of`, and `start` says it shortened it) or given with `--name`, which is refused if it breaks the rule or is taken; `slice rename` changes it while the record is refining, moving a change's folder (its date kept) or a slice's file and rewriting every reference (`depends_on`, `slice:` of batches, decisions and findings), all or nothing; ids of the dated form `S-YYYY-MM-DD-xxxx` written before R86 are still read. Every write is verified and **rolled back** if the slice would not verify, so an illegal move or a step citing a missing criterion leaves nothing on disk. Legal moves: refining to ready or abandoned; ready to building, refining or abandoned; building to blocked, delivered or abandoned; blocked to building or abandoned; delivered to accepted, rework or abandoned; rework to building or abandoned; accepted to rework. **The ready rule (R114)**: `ready` is refused unless the record has at least one criterion and at least one exclusion, of any kind (feat, fix…) and also for a change made of slices, which needs its own, and while a blocking question in its batches is open; the refusal says everything that is missing (the prototype's screens, R107, come later). `verify` checks the same of every record past `refining` (except `abandoned`) opened on or after `READY_RULE_FROM` (2026-11-02, in `src/slice.mjs`); records opened before keep the older rule (a feat without slices needs criteria) and are not rewritten; `accepted` needs `--by owner` (and `--channel chat|cli|view`, default `cli`), every step done, no open finding, every assumed default confirmed (R59) and (for a change in slices) no open slice, and records `accepted: { by, at, channel, assurance }` with `assurance: recorded` (level 0, not signed, R61); the board and the view say "recorded, not signed". The design is in `docs/design/14-slice-format-and-standards.md`; acceptance is as strong as the repository (H4): the agent could type `--by owner`, which is why the plain CI job and the protected `main` stay.
`buddy checkpoint --slice <id>` (which ignores Buddy's own records, `docs/buddy/` and `docs/questions.md`, when it measures and reviews the change) reads the request from the slice record, adds the signals that come from the record (open steps, assumed defaults nobody confirmed, a risk appetite in `docs/context.md` that is neither confirmed nor accepted as assumed) and moves the slice from `building` to `delivered` whatever the decision (`delivered` means the checkpoint ran and its exceptions are shown); a slice that is not `building` is refused. `buddy view` reads `@1` (kind, criteria, steps, who accepted). `@0` was removed. Not yet: evidence on `delivered`; `outcome` written by the checkpoint; the activity log (Q76).

**What the checkpoint measures and who reviews it (R128).** A slice is measured by the patches of the commits that carry its `Slice:` trailer plus its uncommitted work, never by the net change of the files it touched, so another slice's lines in the same file are not counted. Validate stops after 30 minutes (`--validate-timeout <seconds>` or `BUDDY_VALIDATE_TIMEOUT`) with a message and everything it started is ended. The independent reviewer is asked only when validate is green; otherwise the evidence says it was not run. What the scan flags does not stop it (R216): it judges each skip marker and each deleted test (`scan_flags`: the line, whether it is justified, and why), and only one it did not judge or found unjustified is an exception; a verdict that did not justify them all is never reused. It is a read-only agent (`claude -p` on Sonnet, `--model` changes it, tools: Read, Grep, Glob, `git show|diff|log`) that receives the diff in whole files (source, tests, docs, up to 30,000 characters), the criteria and exclusions, and the list of standards and context files Dev read, and is told what the diff left out. The checkpoint reads its session stream: a file left out of the diff that the reviewer did not open keeps the work from being approved, a standard it says is broken or a criterion not met is an exception, and the files it opened are in the evidence (`review_input`). Acceptance also asks for the whole test suite to be green on the code as it is now: a change elsewhere cannot have broken what was checked, and the owner's acceptances rest on one run (`buddy suite`, or any checkpoint that ran the full suite) while it is under 2 days old and was got with the same tools; a project with no suite has nothing to ask. Each change says how to try each of its criteria (`buddy slice try set <name> <AC> --steps "<what to do>" --expect "<what to see>"`, written by Dev while it builds); from the day of the rule (2026-11-05) a change that has criteria with no way to try one does not come out clean, and the reviewer says when a way would not prove its criterion. When every change of a milestone is delivered, `buddy milestone review <milestone>` prints the script of the review, like the demonstration of a sprint review: what was promised and delivered, the whole suite's state, the order to try the changes, and for each one what it is for, how to try it, what to see, what the checks found and how to answer; the owner accepts or sends back each change from it and what they notice becomes a request. A milestone starts only with the owner's go-ahead, recorded by moving it to building; `buddy milestone card <milestone>` is what Buddy presents first, made from the records: the changes in order, the doubts that wait (those that stop the work first), and the assumptions made, with the default taken for each question nobody answered; a change of a milestone that has not started is refused with that pointer. With a milestone planned, Buddy does not wait for acceptance between changes: a delivered change waits for the owner (`buddy digest` lists it) while the next one is built, and the foreseeable costly questions (new libraries included) are asked once at the start of the milestone (R115, R117). A change that is delivered or in rework can go back to `refining` (`buddy move <name> refining`) so the owner can adjust its criteria or exclusions when a finding turns out to be about the goal and not the work; it then goes through `ready` and `building` again and its finished steps stay ticked (Buddy's instructions say how to propose it). A green validate that another change already got on exactly the same code and tests, or an earlier check of the same change, is reused instead of running the suite again, but only while it is under 2 days old and was got with the same system and Node version; the reviewer's verdict is reused only for the same code and the same goal (the criteria, what is left out, the assumptions and how each criterion is tried: `goal_hash`), so a change of goal asks the reviewer again (every evidence records them in `environment`); otherwise validate runs, and the evidence says why in `validate_not_shared`. Every existing test a slice edits is judged by the reviewer one by one (`edited_tests`: the file, whether the edit weakened it, and why); a test with no judgment, or a weakened one, is an exception, and a verdict that did not judge them all is never reused. A prototype screen the reviewer knew was there and could not verify never passes: the check reads `not run` and it is an exception that carries what would let a reviewer verify it next time (`how_to_verify`); the owner may decide that nobody tries again (`buddy slice unverified accept <id> <screen> --by owner`, undone with `unverified undo`), which is recorded, shown on the accept card, and stops being an exception but never becomes a pass. Only the files that carry risk must be opened: source and configuration, and the tests the scan flagged; documentation, records that only moved and the other tests are listed as `not_reviewed` in the evidence and are not an exception. The evidence keeps what the reviewer opened (`reviewer_opened`) and a fingerprint of the measured content (`content_hash`). When the same content gets a different verdict than in the previous round, the reviewer investigates why (what each round read, which verdict holds) and the evidence records the `consistency`: the cause, the files only one round opened and whether the finding holds; a finding that does not hold is set aside (kept in `set_aside`), and the matter reaches the owner only if the finding holds or no cause is found. The third round of a slice with findings still open is handed to the owner (`round` in the evidence). `buddy checkpoint` prints nothing about committing: Dev commits when the slice closes (R88).

## requests (the map of what was asked, R110)
```bash
node core/bin/buddy.mjs requests add "<text>" --source "<where it comes from>"   # prints the new id: RQ1, RQ2...
node core/bin/buddy.mjs requests set <RQ id> --to <change or milestone>          # covered by it
node core/bin/buddy.mjs requests set <RQ id> --excluded "<reason, or the change or milestone that leaves it out>"
node core/bin/buddy.mjs requests set <RQ id> --deferred "<reason>"
node core/bin/buddy.mjs requests set <RQ id> --waiting <question id>              # waiting for the owner's answer
node core/bin/buddy.mjs requests priority <RQ id> must|should|could|none [--why "<reason>"]  # the owner's MoSCoW; Won't is what is excluded or deferred
node core/bin/buddy.mjs requests priority <RQ id> must|should|could --from-prd "<citation>"  # stated by the PRD; never over the owner's
node core/bin/buddy.mjs requests priority <RQ id> must|should|could --proposed --why "<reason>"  # proposed by Buddy; never over the owner's or the PRD's
node core/bin/buddy.mjs requests why <RQ id>                                     # its priority, where it comes from and why, in one line
node core/bin/buddy.mjs requests confirm --priorities                            # the owner confirms every priority Buddy proposed
node core/bin/buddy.mjs requests depend <RQ id> --on <RQ id> [--on ...] [--assumed]  # what it needs first; --assumed: Buddy's proposal
node core/bin/buddy.mjs requests undepend <RQ id> --on <RQ id> [--on ...]        # it no longer depends on them
node core/bin/buddy.mjs requests confirm <RQ id>                                 # the owner confirms its assumed dependencies
node core/bin/buddy.mjs requests order [--json]                                  # the order of the work, with its warnings; writes nothing
node core/bin/buddy.mjs requests list [--open] [--json]                          # --open: only what has nobody yet
node core/bin/buddy.mjs requests remove <RQ id>                                  # only while it has no destination and nothing depends on it
```
One map per project, `docs/buddy/requests.md` (schema `buddy/requests@1`, design/17 §3a): every requirement of the inputs (a line of the PRD, a screen of the prototype) is an item with its id, its text, where it comes from (`docs/inputs/prd.md §2.3`, `prototype: Booking screen`) and its destination: `covered` by a change or milestone (`to`), `excluded` by a change or milestone that leaves it out (`to`, when `--excluded` names one that exists) or for a reason, `deferred` with its reason, `waiting` for a question; no destination means nobody has it yet. `set` replaces the destination; `remove` refuses an item that went somewhere (exclude or defer it instead). Ids never renumber, and a removed id is never given again (`last` keeps the highest one given). The body is a generated view; the front matter is the source of truth. Every write is verified and rolled back if it would not verify. `verify` checks that ids are unique, that each item carries exactly the fields of its destination, that `to` names an existing change, slice or milestone and `question` an existing question, and that there is one map. `slice rename` rewrites the `to` of the items that name the renamed record. **Priority and dependencies (R132)**: an item may carry `priority` (`must`, `should`, `could`; independent of the destination, and an item excluded or deferred reads as `Won't` in `list` and the view, whatever was marked) and `depends_on` (`[{ id, origin }]`: `assumed` when Buddy proposed it, `human` when the owner said or confirmed it; `depend` without `--assumed` is the owner's word). `verify` refuses a dependency on an id not in the map and on the item itself; `remove` refuses an item others depend on. `order` lists the items not excluded or deferred, what others need first, ties by effective priority (Must, Should, Could, none: its own or the highest of what needs it, transitively), then its own, then id, and warns of a request that depends on one of lower priority (`RQ1 (Must) depends on RQ4 (Could): it should be Must too`), of a dependency on an excluded or deferred request, and of a cycle (its requests, and those that need them, go last in id order). No scores, no dates. **Where a priority comes from (R136)**: `priority_origin` is `prd` (stated by the PRD; `priority_why` its citation, `PRD §3.2: P1`), `assumed` (proposed by Buddy; `priority_why` its reason) or `human` (the owner's; `priority_why` optional); a priority with no origin was set before R136 and reads as the owner's. `priority` without flags is the owner's word; `--from-prd` and `--proposed` are refused over the owner's priority, `--proposed` also over the PRD's, and a newer `--from-prd` replaces the PRD's and says from what to what. `list` and the view show `[Must · proposed]`, `[Must · PRD]`, `[Must]`; `list --json` carries the origin; `confirm --priorities` makes every proposed priority the owner's, keeping its reason. Translating another scale to MoSCoW is Buddy's, in conversation; the program only records the result. `verify` refuses an origin or a why without a priority, and a `prd` or `assumed` one without its why. **On the board and the digest**: when the map has items, what has nobody waits for the owner (`2 of what you asked for have no destination yet: Login with SSO [RQ2] | Print [RQ4]`, at most three by their text, then `and N more`), a Must among them on its own line first (`1 Must of what you asked for has no destination yet: Export to CSV [RQ1]`), then the priorities Buddy proposed (`3 priorities proposed by Buddy wait for your confirmation (buddy requests confirm --priorities, or change the ones you disagree with)`), followed by one line of totals (`What you asked for (5): 1 covered, 1 excluded, 1 Must without a destination yet (RQ1), 2 without a destination yet`); when everything has a destination that line says so (`Everything you asked for has a destination (5): 2 covered, 1 excluded, 2 deferred`). An item covered by a change that was abandoned has nobody again; a milestone is not accepted while a Must covered by one of its abandoned changes has not been given a destination again. No map, nothing is shown.

## migrate (once, R87 and R118)
```bash
node core/bin/buddy.mjs migrate --map names.json --dry      # the moves it would make; nothing written
node core/bin/buddy.mjs migrate --map names.json            # { "<old id>": "<name>" }: moves and renames, all or nothing
node core/bin/buddy.mjs migrate                             # with no flat records left, only docs/buddy/changes/ to docs/buddy/backlog/
```
Moves `docs/buddy/changes/` (the backlog of before R118) to `docs/buddy/backlog/`: each folder whole, with its name, through `git mv` when git tracks it (so the files keep their history and the move is staged; untracked files in the folder move with it), else renamed; a folder already in the backlog stops it before anything moves, and a failed move puts back the ones already made. And it moves the flat layout of before R87 into one folder per change in the backlog: every record of `docs/buddy/slices` becomes a change (`<created date>-<name>/change.md`), except one that names an `epic:`, which becomes a slice file in its epic's folder (an epic becomes a change of kind `feat`). Old ids take the names of the map; `depends_on`, `slice:` and `requested_by` follow; the batches of `docs/buddy/questions` and the decisions of `docs/decisions` taken for a slice move into its change's folder (batches as `questions-<n>.md`); a record without steps gets the line that says so. If the result would not verify, nothing is written; run again, it finds nothing to move. Not moved: checkpoint evidence already in `.git/buddy/` and the worker registry, which are local and keep the old ids, like the commits already made.

## index and find (R138, R139)
```bash
node core/bin/buddy.mjs index [--repo <dir>] [--force] [--json]
node core/bin/buddy.mjs find "<words>" [--repo <dir>] [--json]
node core/bin/buddy.mjs decisions [--state <state>] [--repo <dir>] [--json]
```
One reader (`core/src/index.mjs`, `buildIndex`) reads every record in one pass; the board, its page, the digest and `requests order` are built from it in memory, and leave `.git/buddy/index.json` up to date as a by-product for other readers. `index` rewrites the file only when a record changed (the fingerprint of the files read: path, size and time; `--force` always) and prints what it holds in one line, or the index with `--json`. `find` prints one line per change, piece, milestone, criterion, request, question or decision whose text holds every word, case and accents aside: what it is, its id, its text and the file where it lives. `decisions` prints each decision of the log with its id, its Built state, its title and where (`--state` keeps one state). An orphan, a decision with no destination (not built and in no change of the backlog, a backlog change that does not exist or was abandoned, a deferral without its reason, a supersession that names no decision), fails `core/test/decisions.test.mjs`; the board of a repository whose log has the Built column says in one line how many decisions are decided and how many are not built yet. The file is never kept in the history; there is no server and no viewer of its own. Its top-level keys:
- `schema`: `buddy/index@1`; `generated`: when it was built; `fingerprint`: of the files it read.
- `milestones`, `changes`: every milestone, change and piece (a piece has its `change`), by rank: id, title, kind, status, rank, milestone, file, request, criteria, excludes, assumptions, steps (`done`, `total`, the `next` open one), priority, `waits_for` (the changes not yet delivered it waits for) and `abandoned_deps` (as the board reads them, R133, R144), and the file of its latest `evidence`.
- `now`: what is being built, each with its first open `step` (n, total, text); `next`: the first change by rank, in the milestone being worked on, that is not delivered, accepted, abandoned or being built, even when it waits (with its `waits_for`), or null when nothing is left. The board, its page, the digest and Buddy read them from here (R144).
- `requests`: the items of the map of what was asked (destination, priority and its origin, `depends_on`), or null with no map.
- `batches`: each question batch with its slice and its questions (situation, status, blocking, answer) and assumed defaults.
- `evidence`: each checkpoint, summarised: file, slice, when, decision, reasons, checks, the decisions nobody specified, and whether it holds `code_hash` and `files_hash`.
- `decisions`: each row of `docs/requirements-log.md` (an R decision or a P principle of the blueprint): id, date, status, `built` and `where` (its Built column, R110: built, partly, not built, backlog, deferred, superseded or not applicable, then the change, file or reason; null in a log without that column), title (its bold text) and text, refs.
- `problems`: the records that did not read, by file, so none is left out in silence.

## board (radiators R1 and R3)
```bash
node core/bin/buddy.mjs board [--repo <dir>] [--now 2026-10-31T18:00:00Z] [--out board.html] [--json]
```
The board by state, grouped by milestone when there is one (each milestone with its state and how many of its changes are accepted, its changes by state under it, then the backlog; without milestones, one group as before; a delivered milestone is waiting for you to accept) (epic and steps shown, how each acceptance was recorded, and whether its branch is merged: `merged into main`, `waiting to merge`, `branch not found here`, read from git and never stored, R63) and **what is waiting for you**: delivered slices to try and accept, branches whose slices are all accepted and are not in main yet (R62), blocking questions open, what you asked for that has nobody (with the totals of the map of what was asked, see `requests`), assumed defaults not confirmed, a risk appetite not confirmed. A pure function of the records and `--now` (R34): the same files and the same clock give the same bytes; it reads only; plain text, a static page with no external assets, or JSON. Ages are whole units (`<1 h`, `5 h`, `2 d`). Tested against a golden text. Not yet: the pulse (R2) and the other radiators, which need the activity log (Q76).

## digest (R10, and the pulse of R2)
```bash
node core/bin/buddy.mjs digest [--repo <dir>] [--since <ISO>] [--now <ISO>] [--stale-minutes N] [--mark] [--json]
```
What changed since the Product Owner last looked, what waits for them, what may be stalled, the checkpoints that ran and the workers that finished (R65: an absent person cannot be notified, so they ask). It reads only; `--mark` then records the look in `.git/buddy/last-looked` and the next digest starts there (the first one reports everything as new). Without an activity log (Q76) it reports the present state of what changed (by each slice's `updated`), not every transition. `buddy board` carries the pulse on every slice being built: `Dev <id> seen 5 min ago`, `STALLED? Dev <id> last seen 3 h ago` after 30 minutes of silence (a starting value to measure), or `no Dev registered`.

**How many times you were asked, and how long it waited for you.** The digest adds one line per change that asked the owner something since the last look (`Alpha [alpha]: asked you 3 times; it waited for you 1 d 3 h (1 without a date)`) under the all-time total of its milestone (`v1: you were asked 3 times; it waited for you 1 d 3 h in all`); the checkpoint exceptions go on their own line under each (`1 checkpoint exception, waited 2 h for a decision`), never among the times the owner was asked nor in that time; `--json` carries the numbers in `minutes` (`exceptions`, `exceptions_waited_minutes`, `exceptions_undated` apart from `asked`, `waited_minutes`, `undated`). `buddy minutes [<change or milestone>] [--json]` prints the same for every change, a milestone, or one change with each of its events, all time. Counted per change and its pieces: each question of its batches (from the batch's creation to the owner's answer), each acceptance (the pieces accepted with their change are one; from the latest checkpoint before it, else the commit that wrote `status: delivered`, to `accepted.at`) and, apart, each checkpoint exception (from its time to the slice's next checkpoint or its acceptance). It is the time something waited for the owner, not their working time, read only from the records and their git history; an event without one of its dates is counted and left out of the time, and waits that overlap count once. A date the record keeps as a day is read as a day.

## resume (after a cut, R53 and R57)
```bash
node core/bin/buddy.mjs resume [<slice id>] [--repo <dir>] [--now <ISO time>] [--json | --handover]
```
Without an id, the slices in flight (building, rework, blocked). With an id, the brief to relaunch Dev, built from the files only: request, criteria, steps done and the next one, what the Product Owner answered and what was only assumed (not to be asked again), decision records, open questions (blocking ones marked), and the git state. A pure function of the files, the git state and `--now`; it reads and writes nothing, except with `--handover`, which writes the brief to `.git/buddy/handover/<id>-dev-<time>.md` and prints its path: Buddy raises Dev with that file, and the checkpoint writes the reviewer's hand-over there too and records both with their fingerprints in the evidence (R134). `.git/buddy/` holds what is not worth keeping in the history: hand-overs, workers, settled commits, the digest mark. A slice that is not building, rework or blocked is refused.

## settle (R54, R91, R124)
`buddy settle [--since <commit>]` reads the commits made **without a change** (no `Slice:` trailer, and not only Buddy's own records) since the last settle, classifies them after the fact, runs validate and the scan, and says whether the owner has to look. A *small correction* with green checks asks nothing; it is a *grew* (it adds a feature, or is over 200 lines or 8 files) when it should become a change, even afterwards. It flags, for the owner: failing checks, deleted tests, skipped checks, protected files, fewer assertions, something specified changed (`docs/inputs/`, `docs/standards/`, `docs/context.md`), and behaviour changed with no test. A small correction leaves **no record in `docs/buddy/`** (R91): the evidence is kept in `.git/buddy/settled/` and `buddy digest` lists it ("Quick fixes settled (n, m need your look)"). The vibe playbook (`skills/vibe/SKILL.md`, a skill of the plugin) tells Buddy how to code with the owner in the same conversation and when to settle: at commit or when asked.

## The commit check (R111, R121, R123)
`core/src/commitcheck.mjs` checks a commit message with the rules Buddy needs and nothing to install: the Conventional Commits header (the vocabulary and limits of config-conventional), `Buddy-Fix:` on a `fix` (an error) and `Slice:` on a `feat` (a warning, and the slice must exist and not be abandoned). It replaces commitlint, which loaded hundreds of modules and took seconds per commit on a machine with a real-time antivirus; checking a message now takes about 50 ms. `core/bin/commitcheck.mjs --edit <file>` runs it (this repository's `commit-msg` hook).

The plugin brings a `PreToolUse` hook (`core/hooks/hooks.json`, `core/bin/commithook.mjs`): before Buddy or Dev runs `git commit` in a Buddy project (a folder with `docs/buddy/`), it reads the message out of the command (`-m`, several `-m`, `-am`, `--message=`, `-F` file, a heredoc, `$(cat <<EOF)`), refuses a bad one with what to fix (exit 2), and runs gitleaks on what is staged: a secret stops the commit, and gitleaks not installed is *not run* and says so, never a pass. It writes nothing into the project and comes and goes with the plugin. Every `git commit` of a chained command is judged, and with `-a` the tracked files it adds are scanned too (their whole content, so an old secret in a file you touch also stops it). A commit whose message the command does not show (an editor, `--amend --no-edit`) is not judged, and a missing `Slice:` on a `feat` is only a warning the hook cannot show, so Dev is told in Buddy's instructions; commits made by hand outside Buddy are checked by the project's CI (R112).
