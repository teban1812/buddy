# A new project

`buddy <command>` is Buddy's program, run as his instructions say. If the project has no `docs/context.md`, it has not been created with Buddy yet:
1. Say the library first: `buddy init --list-profiles` reads the library that will be used and ends with its `Library:` line (which library and version, why that one, and how to use another for this project with `--library` or for every new one with `buddy library --set`); tell the owner that line in one sentence before anything else. If the owner names another library, use it with `--library` in every command below, or set it with `buddy library --set`. If a library cannot be reached (it may be private), help the owner get access to it, or offer `--no-library`.
2. If the owner handed over a PRD or a prototype, read it now by loading the `intake` skill of this plugin, so you do not ask what it already says. If the owner brings no PRD and no prototype, offer discovering the product as the first step of this same conversation, and if they accept load the `discover` skill of this plugin: what it confirms is written into the business context and the map of requests, so step 6 starts from it instead of asking again. If the owner speaks to you in a language other than English, or the PRD or the prototype is written in one, ask now, once, in which language to keep the project's documentation (the rule is in your instructions: *The documentation language*); with no such sign ask nothing: the documentation is in English.
3. Ask the library's general questions, which `--list-profiles` lists, one at a time in the owner's terms, offering the choices when a question has them and saying why it is asked. An answer the PRD already gives is shown to the owner to confirm, not asked again.
4. Recommend a profile in one line with its reason, from the answers, the inputs and each profile's line in the list — when the owner handed over a PRD or a prototype; the owner chooses. Then ask that profile's questions (`buddy init --questions --profile <profile>`) the same way, and where the repository will live: GitHub, Azure DevOps, or neither for now. **With no PRD and no prototype**, do not choose a profile yet: skip to step 5 with `--no-profile`; the profile is recommended and brought at the end of discovery, from what discovery found.
5. Write the answers, in the owner's words, to a JSON file outside the project (`{ "<question id>": "<answer>" }`; a question the owner leaves open is left out). With a PRD or a prototype, run `buddy init --profile <their choice> --host github|azure|none --answers <file>`. **With no PRD and no prototype**, run `buddy init --no-profile --answers <file>` (omit `--answers` if there were none): it brings the context, the library's general standards with `design.md` and its themes, and no template or profile standards. Each answer goes into `docs/context.md` in its question's section, and fills its open value in the project's standards. Tell the owner the `Library:` line again, the pipeline line (when a profile was chosen, where the project's checks will run on every push) and the `Health:` lines in plain words: an open value left to be defined is a decision still owed; if the project is not born healthy, fixing that comes before the first change.
   **When the owner chose a language other than English**, init still wrote the context in English (the program writes only English). Right after init, before anything else is added to it, rewrite `docs/context.md` whole in that language: the `title` of its header, its title line, its introduction, every section heading, the line that says the business is still to be told, and each question of the library with its answer, worded as you asked it and as the owner answered ("Asked because" and its reason too). Keep each line's origin tag and date as init wrote them: `human`, `assumed` and `unknown` are the program's words, never translated. Add to the header `risk_section: <the heading you gave the risk section>`, written exactly as the heading; if that section has no line yet, give it one that says what is costly to get wrong is still to be told, ending in `unknown`, because the program reads the risk lines in the section the header names and refuses a context whose named section is missing or has no line. Then write the language line (`buddy context add`, as *The documentation language* says) and run `buddy context check docs/context.md` to see the context accepted. When the owner was asked and chose English, only the language line is added.
   If init says the folder already holds a project (no template was copied), the checkpoint, `buddy suite` and `buddy settle` still need a way to run its tests: an npm `validate` script or a `validate.sh`. Look for one; if there is none, before the first change propose to the owner one that runs the tests the project already has (show the command, say how long it takes), add it as a small correction once they agree, and run it once to see it pass. If the project has no tests, say so plainly: until it has some, the checks have nothing to run, and the first change should add them.
6. Have a short conversation about the business: why the software exists and the outcome that matters, who uses it, the constraints, and what would be costly to get wrong, **and what is cheap to get wrong**. Write each statement with `buddy context add` in the owner's words, naming the section by its heading as the context has it. In a context born in another language, the owner's first risk statement replaces the line that says it is still to be told: `buddy context confirm docs/context.md --line <n> --text "<their words>"` (`buddy context check docs/context.md --json` gives its number). Lines you infer are added with `--assumed` and confirmed with the owner before they are relied on. The risk lines must be confirmed before building. When the owner hands over a PRD or a specification, draft these lines from it instead of asking what it already says (the `intake` skill).
   Then write the project's own `README.md`, short, in the project's language: what the software is for and who uses it (from `docs/context.md`), how to set it up, run, stop and test it (from `docs/base-application.md` and the scripts in `package.json`, when the base brought them), and where its context, standards and decisions are. Never copy a template's README (a library that still ships one gave the base's, not the project's: replace it). Only what is true today; when a later change alters how the project runs or what it is, its Dev brings the README up to date in the same change.
7. Run the profile's steps, which `buddy init --questions --profile <profile>` listed (a security checklist, say): init copied each to `docs/steps/<step>/` (its `step.md` says its items, their clauses and its triggers) and wrote its record where the step says. **Not at birth**: a step's record answers how the product is built, so draft it once it is clear what will be built, when the first milestone's plan is studied (its changes, their criteria and assumptions), and present it with the milestone's card, before any change is built. Tell the owner at birth, in one line, that it comes then. When you draft each record, from the requirements (the PRD, the context, the answers) and the plan: A line marked `decided` is decided by the base application, in the file it names: never ask it, nor show it as a question. Replace each line marked `unknown` with your answer and its reason, ending in `assumed`: `- <id>: <text> (<clause>). Answer: <answer>. Because: <reason> \`assumed\``. Then go through those lines with the owner one by one, in their terms; record each one they confirm with `buddy context confirm <record> --line <n> --by owner`, and a correction with `--text "<the corrected line>"`. The Product Owner then approves the record as a whole: before you ask for it, show him every line of it in his terms, the `decided` ones too, each with the file that decides it (shown, not asked). Record his approval with `buddy context approve <record> --by owner`. Never run `confirm` or `approve` with `--by owner` on your own: only after the owner said so in the conversation. Ask for it as a question of its own (its lines, then the approval of the whole record), never folded into an "ok" to other things such as the context, the screens, the priorities or the milestone: it is his signature on the record, and it must be plain what he signed. Until every line is decided or confirmed and the record is approved as it is now, no change can move to building (it is refused, naming the record and what to do) and the board lists it as waiting for the owner; any later edit of the record needs his approval again.
   When the library has normative documents, init copies their index to `docs/standards/normative.md` (never a document) and `--questions` lists them. It says which document and version each id means: resolve each clause the standards and the records cite (such as SCS v2.0 clause 4.2) through it. Never fetch a link it gives (they may be private pages): work from the clauses as cited, and when a decision needs the document itself, tell the owner so.
